# LightTodo 稳定性修复设计

- 日期：2026-07-11
- 状态：待书面确认
- 范围：数据安全、核心正确性、交互与动效、可访问性、架构和测试
- 依据：当前代码审查、现有测试结构与构建环境检查

## 1. 背景与目标

本轮不是视觉改版，也不是全量重写。目标是在保持现有产品形态的前提下，消除会造成数据丢失、数据复活、误删外部数据、提醒失效和编辑状态错乱的问题，并建立后续可以持续迭代的结构与测试基线。

设计采用“总路线图 + 四个可独立交付的修复项目”。项目按风险顺序推进，每一项结束后都应处于可构建、可测试、可发布的状态：

1. 数据安全：笔记生命周期、日历写入边界、备份原子性、共享附件清理。
2. 核心正确性：编辑加载与并发、日期时区、提醒、排序、滚轮、重复日历事件。
3. UI、动效与可访问性：数据与动画解耦、列表退出、共享转场、选择模式、语义与对比度。
4. 架构与测试加固：拆分大文件、解除跨 feature 依赖、补行为测试、更新架构文档。

## 2. 成功标准

完成全部项目后，系统必须满足以下结果：

- 删除笔记后，任何生命周期回调都不能把它重新写回数据库。
- 用户把现有笔记清空时，空内容会被保存；新建且从未输入内容的笔记不会产生空记录。
- 外部日历事件在任何路径下都严格只读；只有本应用创建的事件可以被更新或删除。
- 用户主动清空数据后，应用重启不会从旧备份恢复；新安装仍能在合适条件下恢复有效备份。
- 任意一次备份写入中断，都至少保留上一份可验证的完整备份。
- 两篇笔记共用同一附件引用时，删除其中一篇不会破坏另一篇。
- 编辑页未加载完成时不能保存或删除；重复点击不会重复创建或重复提交。
- 日期、提醒和排序使用本地日期语义，在夏令时切换和时区变化后仍正确。
- 数据变更不等待动画结束；关闭系统动画时，核心操作仍立即、完整地执行。
- 关键文字颜色达到 WCAG AA，交互目标不小于 48dp，非文字控件具备可读语义。
- 新增回归测试直接验证行为，而不是主要依赖源码字符串断言。

## 3. 非目标

以下内容不纳入本轮：

- 更换导航框架或重写整个 Compose UI。
- 引入多日待办；编辑页统一为“一个日期 + 可选开始/结束时间”。
- 云同步、多人协作或新的账号体系。
- 全新品牌视觉或大规模信息架构调整。
- 与必要迁移无关的数据库重写。
- 对第三方日历提供方行为做无法保证的一致化封装。

## 4. 方案选择

### 4.1 采用方案

采用按风险分层的四项目方案。其核心是先修复不可逆的数据风险，再修复时间、编辑和提醒等正确性问题，随后调整动效与交互，最后收束结构和测试。

四个项目分别有自己的验收门槛，但共享本文定义的数据契约和架构边界。后续实施计划不得通过临时绕过这些契约来换取局部完成。

### 4.2 未采用方案

- 按页面逐页修：容易在同一数据链路中留下不一致路径，例如首页删除修好而批量清理仍误删外部日历。
- 一次性重写：改动面过大，难以证明数据迁移和行为兼容性，也不利于逐步回归。
- 只补 UI 防抖和确认框：无法解决仓储层、备份层和系统集成层的根因。

## 5. 全局设计约束

### 5.1 数据所有权

- Room 数据库是应用内状态的事实来源。
- `calendarCreatedByApp = false` 的事件属于外部系统，本应用只能读取和建立本地映射，不能更新或删除提供方记录。
- `calendarCreatedByApp = true` 的事件可由本应用更新或删除。
- 本地完成或删除外部事件映射，只改变本地待办，不改变系统日历事件。
- 文件清理属于数据库提交后的派生操作。清理失败最多造成暂时残留，不能造成仍被引用的文件丢失。

### 5.2 生命周期与并发

- 删除是终态。进入删除状态后，自动保存、页面销毁和重复点击均不得再次写入该实体。
- 所有保存操作必须串行化，并对同一编辑会话保持幂等。
- 页面导航只能由一次成功结果触发，不由多个并发协程分别触发。
- UI 的 Loading、Ready、Saving、Deleting、Error 必须是显式状态，不能用默认空表单代替加载状态。

### 5.3 动效与业务状态

- 数据写入、完成、删除和提醒处理不依赖固定延时。
- 动画是业务结果的可取消视觉投影，不是提交操作的时钟。
- 系统动画比例为 0 或启用减少动态效果时，操作仍能立即完成。
- 动画期间不可见的控件不得继续获得焦点、点击或无障碍访问。

### 5.4 失败策略

- 数据库提交优先保证本地一致性；可重试的系统副作用通过明确队列或协调器完成。
- 备份只有在全部文件写入并通过读回校验后才能发布为当前版本。
- 恢复、导入和 SAF 目录选择失败时，不写入“成功”状态，也不替换当前有效配置。
- 用户可感知的失败必须进入 UI 状态或日志事件，不能只被协程吞掉。

## 6. 项目一：数据安全

### 6.1 笔记保存与删除

当前风险来自页面销毁时无条件保存：删除发起后页面返回，`onDispose` 又使用仍保留的 `noteId` 执行 upsert，从而复活刚删除的记录；同时，现有笔记被清空后会被“空内容提前返回”拦截。

目标设计：

- 编辑会话引入 `Active`、`Deleting`、`Deleted` 三种生命周期状态。
- 自动保存改为加载完成后的脏状态防抖保存；所有保存经过同一互斥入口。
- 返回操作调用 `flushAndAwait()`，确认当前保存完成后再导航。
- `onDispose` 只取消观察与协程，不执行数据库写入。
- 删除前先原子地把会话切到 `Deleting` 并取消待执行的自动保存；成功后进入 `Deleted`。
- `Deleting` 和 `Deleted` 状态下所有保存入口都是无操作。
- 新笔记仅在有标题、正文或附件时首次创建；已经存在的笔记即使标题和正文为空也应更新，以表达用户主动清空。
- 删除失败时回到 `Active` 并显示错误，不静默退出页面。

### 6.2 附件引用安全

附件引用可能因导入去重而被多篇笔记共享，因此不能根据单篇笔记的差集直接删除文件。

目标设计：

1. 在数据库事务中提交笔记及附件引用的新状态。
2. 事务成功后重新查询全库仍被引用的附件集合。
3. 只删除“旧引用集合减去全库引用集合”的文件。
4. 每个实际删除动作前再次确认引用，避免并发编辑导致检查后使用问题。
5. 文件删除失败记录为可重试清理，不回滚已经成功的笔记内容。

导入流程可以继续按内容或稳定引用去重，但必须接受共享引用是合法状态。后续可加入周期性孤儿文件清理，清理规则仍以全库引用为准。

### 6.3 日历只读边界

所有日历写操作集中到一个纯策略与一个执行协调器，禁止用例或页面直接根据 `calendarEventId != null` 推断可删除。

`CalendarMutationPolicy` 的核心判定：

- 外部事件：允许读取、建立或更新本地映射；拒绝提供方 update/delete。
- 本应用事件：允许提供方 update/delete。
- 没有关联事件：只执行本地操作。

单条删除、批量删除、清理已完成、编辑同步和设置页手动同步必须走同一策略。针对本应用创建事件的删除，数据库事务同时删除本地待办并写入 `PendingCalendarMutation` 清理队列；协调器在具备权限时执行提供方删除，失败后保留重试记录。外部事件绝不进入删除队列。

这样既保证本地删除立即生效，也避免权限暂时缺失时留下无法追踪的应用自建日历事件。

### 6.4 备份启动协调

恢复和自动备份不能在应用启动时竞争。引入唯一的 `BackupInitializationCoordinator`，删除 Application 与 Activity 中互相独立的恢复启动路径。

启动状态机：

1. `Checking`：检查本次安装是否已经完成首次恢复判定。
2. `Restoring`：本地数据为空且属于新安装时，尝试选择最新有效备份。
3. `AwaitingPermission`：旧系统需要存储权限且用户尚未决定时，暂停自动备份。
4. `Settled`：恢复成功、没有备份或用户明确跳过后，才启动自动备份观察。

使用 `noBackupFilesDir` 中的安装级恢复标记区分“同一次安装中用户主动清空”与“卸载后重新安装”。标记会跨进程启动保留，但不会被系统云备份带到新安装：

- 同一次安装已完成首次判定后，即使数据库为空，也不在每次启动时自动恢复。
- 重新安装后标记不存在，可从有效便携备份恢复。
- API 29 以下若仍在等待权限，不发布空备份覆盖旧数据；用户明确拒绝后结束本次自动恢复判定。

首次引入该标记的版本还要区分“旧版本升级”和“真正的新安装”。协调器结合 PackageManager 的 first/last update 时间与旧数据库/偏好痕迹判定：升级且数据库为空时只种下已判定标记，不自动拉回旧备份；当前安装确为新安装时才进入自动恢复。该判定单独做纯函数并用升级、覆盖安装、卸载重装和系统恢复样本测试，不能散落在 Activity 条件分支中。

空数据库也必须写成有效的空快照。它代表用户真实状态，而不是“没有可备份内容”。

“清空全部”和使数据集变为空的批量操作会触发高优先级空快照，不等待普通防抖窗口。若外部目标当前不可写，本次安装的恢复标记仍能阻止重启复活数据，UI 同时说明便携备份尚未同步；目标恢复可写后优先发布空代际，缩短卸载前仍残留旧备份的窗口。

### 6.5 原子便携备份

直接文件目录和 SAF 文档树使用同一代际协议：

- 每次备份写入不可变的 `generation/<id>/` 内容，包括数据、附件索引、文件大小与校验和。
- 保留两个发布槽位 `manifest-a` 与 `manifest-b`，每个清单包含单调递增序号和完整代际摘要。
- 写入时选择非当前槽位：先创建新代际，逐项写入，再读回校验；只有校验通过才写发布清单。
- 读取时验证两个槽位，选择序号最高且代际完整的一份；若最新槽位损坏，回退到另一份。
- 新代际成功发布后才清理超出保留策略的旧代际。
- 兼容读取现有扁平 v2 备份；第一次成功写入新协议后再按保留策略清理旧格式。

SAF 不保证重命名原子性，因此不能依赖“临时文件改名”。双清单槽位加不可变代际确保一次部分覆盖最多损坏一个发布槽位。

抽象 `PortableBackupDestination` 会话接口，统一提供 list、openRead、openWrite、stat、delete 与目录解析。直接文件和文档树只实现目标适配，不各自复制备份算法。会话缓存目录与文档 URI；附件采用流式传输，已存在且摘要一致的内容不重复写入，避免整文件读入内存和逐文件重建查询器。

用户选择新的 SAF 目录时，先在临时会话中完成可读写验证以及所需导入/恢复。只有成功后才持久化 URI；失败继续使用原目录。

### 6.6 项目一验收

- 删除笔记并立即返回、旋转屏幕或触发页面销毁，记录均不复活。
- 清空现有笔记会保存空记录；空白新建页退出不产生记录。
- 单删、批量删除和清理已完成均不会删除外部日历事件。
- 本应用事件删除失败会留下可重试任务，权限恢复后可以完成清理。
- 在备份每一个写入阶段注入失败，恢复仍能选择上一份有效代际。
- 清空全部数据、重启应用不会恢复旧内容；模拟新安装则可以恢复最新有效快照。
- 两篇笔记共享附件时，删除任意一篇后另一篇仍可读取附件。

## 7. 项目二：核心正确性

### 7.1 编辑页状态机

`TodoEditViewModel` 暴露封闭 UI 状态：

- `Loading`：正在加载现有待办，所有提交和删除控件禁用。
- `Ready(FormState)`：允许编辑和校验。
- `Saving`：锁定重复提交，保留当前表单用于反馈。
- `Deleting`：锁定全部写操作。
- `Error(previousState, message)`：展示错误并允许安全重试。

新建页在默认值初始化完成后进入 Ready；编辑页必须在实体加载完成后进入 Ready。保存和删除经过同一提交互斥锁，成功只发送一次导航事件。标题等必填校验在进入仓储层前完成，不能用未加载的空表单覆盖已有数据或创建空白待办。

### 7.2 本地日期模型与数据库迁移

`dateMillis` 把本地日期伪装成瞬时时间，固定毫秒加法在夏令时切换日会偏移。新模型使用：

- `LocalDate` 作为日期事实。
- 数据库存储 `dateEpochDay`。
- 开始和结束时间继续存储本地分钟数。
- 需要触发系统提醒时，才使用当前 `ZoneId` 把本地日期时间转换为 Instant。

迁移分阶段进行：新增 `dateEpochDay`，按迁移时设备时区把现有 `dateMillis` 转为 LocalDate，并在一个兼容版本中保留旧列。新代码只以 `dateEpochDay` 为准，同时在备份 v3 中保存与时区无关的日期。导入 v2 时使用明确的旧格式转换器。

历史数据没有保存创建时区，因此无法对曾经跨时区且已经发生偏移的日期做无损推断。迁移会记录转换统计，并在发布前用真实样本验证；这是现有数据模型的固有限制，不通过猜测偏移来“修正”用户数据。

夏令时规则明确为：不存在的本地时间按平台时区规则向后调整到首个有效时间；重复时间默认采用较早偏移。发生调整时编辑页给出可理解提示。

### 7.3 提醒生命周期

- 提醒触发时间是由 LocalDate、LocalTime 和 ZoneId 计算出的缓存，不是日期事实来源。
- 启动、重启、系统时间变化、时区变化以及精确闹钟权限变化后，统一执行 `ReminderRescheduler`。
- API 31 以上申请精确闹钟权限前不先默默固定为非精确结果；从设置页返回且权限已授予时立即重新调度。
- 无权限时采用明确的降级策略并在 UI 说明精度，而不是表现为已获得精确提醒。
- `ReminderActivity` 的“完成”动作必须等待挂起用例返回后再 finish；处理期间按钮禁用，失败则保留页面并显示错误。
- 通知 action、Activity 与编辑页都调用同一提醒完成用例，避免不同入口拥有不同事务顺序。

### 7.4 日历重复事件

读取系统日历改用 `CalendarContract.Instances` 获取时间窗口内的实际 occurrence，写入本应用事件仍使用 Events。

数据表新增可空且唯一的 `calendarOccurrenceKey`。该 key 由“提供方命名空间 + series identity + logical occurrence anchor”编码或哈希得到：

- series identity 优先使用提供方的 `UID_2445`，不可用时退回 original event ID 或 event ID。
- 重复事件例外优先使用 `ORIGINAL_INSTANCE_TIME` 作为 logical anchor；普通 occurrence 使用 `BEGIN`。
- 本应用创建的非重复事件保留 event ID 作为直接关联，并生成对应 occurrence key。
- 没有关联的本地待办为 null；SQLite 唯一索引允许多个 null。

这比单纯的 `eventId:beginMillis` 更能承受重复事件例外被移动。Android 提供方并不保证所有来源都有跨设备稳定 UID；当稳定字段缺失且开始时间变化时，不进行模糊的完成状态转移，以免把一个 occurrence 的 `isDone` 错给另一个。同步会把旧映射标记为失效并创建新 occurrence，诊断结果记录降级原因。

迁移时移除 `calendarEventId` 的唯一约束。已有映射先写入 legacy key；首次同步以事件 ID、保存的本地日期和开始时间做精确或唯一匹配，成功后升级为新 key。若旧的重复事件记录无法唯一匹配，则清除其日历链接并保留为普通本地待办，再导入实际 occurrences，优先避免静默丢失用户状态。本地完成状态以 occurrence key 保存，后续同步更新标题和时间等外部字段时不得覆盖 `isDone`。

所有同步入口使用同一个 `CalendarSyncCoordinator` 和互斥锁，包括设置页手动同步，避免自动同步与手动同步并发写入。

### 7.5 排序和滚轮

首页排序统一为：

1. 有日期的待办在前，无日期待办在后。
2. 按 `dateEpochDay` 升序。
3. 同日按开始时间升序，无开始时间排在有时间之后。
4. 最后按 `createdAt` 和稳定 ID 排序，避免列表抖动。

滚轮选择器改为受控组件：参数输入当前 items 与选中值，回调输出变化，Composable 本身返回 Unit。列表状态只保留一个来源；items 数量或标识改变时重新规范化索引并滚动到有效位置。月份从 31 天切到 28 天时，日期先 clamp 再同步滚轮，不让旧闭包继续使用初始长度。

### 7.6 项目二验收

- 慢加载期间快速点击保存或删除不会写入空数据，也不会重复创建。
- 双击保存、连续返回和保存失败重试均只产生一次有效提交。
- 在 America/New_York 等时区的春季和秋季切换日，09:00 仍表示本地 09:00。
- 修改系统时区或时间后，提醒会按新的本地语义重新调度。
- 授予精确闹钟权限返回应用后，无需重新编辑待办即可升级调度。
- 重复日历事件的每个 occurrence 可独立显示和完成，外部完成状态不会被同步复原。
- 跨月切换 31、30、29、28 天时滚轮不越界，选中日期符合 clamp 规则。
- 首页日期排序、时间排序和稳定次序均有行为测试覆盖。

## 8. 项目三：UI、动效与可访问性

### 8.1 完成与列表退出动效

当前固定延时先播放动画、后写数据库，会让动画取消等同于业务取消。新流程：

1. 用户点击完成后立即提交本地变更。
2. UI 把当前行快照放入短生命周期的 `TransientExitRegistry`。
3. 数据查询移除真实行后，快照独立完成不超过约 280ms 的退出动画。
4. 动画结束或被取消后立刻清理快照。
5. 数据提交失败时撤销乐观状态并展示错误。

LazyColumn 中不得长期保留 `AnimatedVisibility(false)` 的零高条目。普通删除直接移除；需要退出效果的条目只由临时注册表持有到动画结束。

### 8.2 编辑器共享转场

- 列表卡片与笔记编辑器共享同一几何信息和进度源，移除两套重复测量状态。
- 转场过程中明确设置输入、焦点和语义可用区，预览层和编辑层不会同时可交互。
- 返回动画按剩余进度计算时长，不使用固定长延时。
- 减少动态效果时退化为短淡入淡出或无动画。
- 一次性包装组件直接内联或收敛为少量 `MotionModifiers`；真正包含共享状态和协调逻辑的组件保留独立文件。

### 8.3 选择模式与页面结构

选择模式是当前页面的显式状态。进入选择模式后禁止左右手势切换 Pager，保证选择工具栏和浮动操作区不会因滑页消失。点击另一个标签时先清除当前选择状态，再切换页面。

所有破坏性操作使用一致规则：无法撤销或会影响多个条目时确认；单条且提供可靠撤销时可以直接执行。确认文案必须说明影响的是本地待办、应用创建的日历事件，还是仅解除外部映射。

编辑页不再展示看似支持多日任务的独立开始日期和结束日期。结构统一为一个日期、可选开始时间、可选结束时间，与当前数据模型保持一致。

### 8.4 颜色、尺寸和语义

亮色主题将颜色角色拆为“强调色填充”和“文字/图标内容色”：

- `#FF9F0A` 继续用于较大面积填充，其上使用黑色内容。
- 品牌文字/图标使用 `#9A5700`，对白底约 5.62:1。
- 次级文字使用 `#6D6D73`，对白底约 5.14:1。
- 逾期文字使用 `#C5221F`，对白底约 5.80:1。
- 深色主题逐项以实际背景验证，普通文字至少 4.5:1，大号文字和非文字边界至少 3:1。

所有点击目标最小 48dp，包括时间步进、媒体缩略图操作、标签和图标按钮。自绘或 `pointerInput` 控件增加 role、label、stateDescription 和 click action；滚轮容器提供当前值及增减语义，重复绘制项不重复暴露给读屏。标题层级和分组使用 heading 或 pane 语义。

### 8.5 项目三验收

- 完成操作在动画中断、页面切换和系统动画关闭时都能持久化。
- 列表长时间使用后不存在持续累积的不可见条目。
- 笔记转场期间只有一个界面层可点击、可聚焦、可被读屏访问。
- 选择模式下无法滑到一个没有选择工具栏的页面；标签切换会安全清除选择。
- 关键颜色通过自动对比度检查，所有目标尺寸和自绘控件通过 Compose 语义测试。
- 字体放大、亮暗主题和减少动态效果下，布局与核心操作可用。

## 9. 项目四：架构与测试加固

### 9.1 模块边界

保持现有单 app module，但执行清晰依赖方向：

`feature UI -> ViewModel -> use case -> repository interface -> data/integration implementation`

共享 UI 不能放在某个 feature 包内再被其他 feature 反向依赖。具体调整：

- 笔记启动种子与转场 key 移到共享 motion contract。
- Markdown 渲染移到 `ui/markdown`。
- 时间滚轮移到 `ui/picker`。
- 首页和设置页不再导入 noteeditor 或 todoedit 的内部 UI 类型。
- 系统日历、文件和提醒均通过 use case 或端口进入 feature，不允许 Screen 直接调用实现类。

### 9.2 大文件拆分

`PortableBackupStore` 拆为：

- 备份格式 codec 与版本迁移。
- generation writer。
- generation reader 与候选选择。
- attachment mapper/transfer。
- destination session 及 direct/SAF 适配器。

`NoteEditScreen` 拆为：

- 路由与状态收集层。
- 编辑器内容组件。
- 媒体区域。
- 对话框与底部面板。
- 共享转场 host。

拆分依据是责任和测试边界，不以固定行数为目标。纯 UI 子组件保持参数受控，不直接获取仓储或导航对象。

### 9.3 测试结构

源码字符串测试只保留用于架构边界和禁止依赖规则；业务正确性由可执行行为测试覆盖。

单元与集成测试重点：

- 笔记删除终态、空内容保存、并发 flush。
- 共享附件引用与清理失败。
- 日历 mutation policy、批量删除、清理队列和同步互斥。
- 备份每个故障注入点、双清单回退、空快照、新安装判定、v2 导入。
- LocalDate/ZoneId 转换、DST gap/overlap、时区变化后的提醒重排。
- 编辑状态机、重复提交、排序和动态滚轮规范化。
- Room schema migration 与 legacy occurrence 升级。

Compose 或设备测试重点：

- 编辑页 Loading 时按钮不可用。
- 31 天到 28 天的日期滚轮交互。
- Pager 选择模式。
- 完成动画取消与减少动态效果。
- 媒体、标签、滚轮和标题的语义树。
- ReminderActivity 等待成功后关闭、失败时保留。

测试替身应在端口边界注入：可控制失败阶段的备份 destination、记录调用的 calendar gateway、可推进时间的 clock、可选择 ZoneId 的 time resolver。不要通过真实系统提供方制造难以复现的单元测试。

### 9.4 文档与可观测性

- 更新 `docs/ARCHITECTURE.md`，删除已经失效的“缺少 use case/gateway”和单体 Repository 描述。
- 记录数据库与备份格式版本、恢复状态机和日历所有权规则。
- 关键后台任务产生结构化结果：成功、跳过原因、权限缺失、可重试失败、永久失败。
- UI 只展示用户可操作的信息，详细诊断写入受控日志，不记录笔记正文或附件内容。

### 9.5 项目四验收

- feature 之间不存在对其他 feature 内部 UI 类型的反向导入。
- 两个大文件按责任拆分，核心解析、选择和状态逻辑可独立测试。
- P0/P1 回归均由行为测试覆盖，源码测试不再充当运行时正确性的主要证据。
- 架构文档与实际包、端口和启动流程一致。
- 全量构建、单元测试、Lint 和目标设备测试通过。

## 10. 数据与格式迁移

预计包含三类显式迁移：

1. Room：新增 `dateEpochDay`、`calendarOccurrenceKey` 和待处理日历清理表，移除 eventId 唯一约束并建立 occurrence key 唯一索引。
2. 备份：写入 v3 本地日期格式与新 generation 协议，继续读取 v2。
3. 安装状态：首次创建 no-backup 恢复标记；旧版本升级视为同一安装，只有在数据库为空且从未完成新协调器判定时执行一次兼容检查。

每个迁移必须具备：旧样本夹具、升级后数据断言、重复运行安全性、失败时不发布新状态。发布前保留一份由旧版本生成的真实脱敏备份做端到端恢复验证。

## 11. 发布与回滚策略

- 四个项目按顺序合并，不把跨项目未完成的中间状态发布给用户。
- 数据库迁移先扩展后切换；兼容期保留旧日期列，降低不可逆回滚风险。
- 新备份读取器先支持 v2 与 v3，再启用 v3 写入；旧备份不会在第一次读取时被删除。
- 新日历策略上线后，外部事件保护默认开启且不可被旧路径绕过。
- 每个项目发布前使用脱敏数据副本执行升级、操作、重启和恢复演练。
- 出现问题时可以停止后台协调器与新格式写入，但不能回滚到会删除外部数据或覆盖有效备份的旧行为。

## 13. 后续实施计划的粒度

设计确认后生成一个总路线图和四份实施计划。每份计划会把工作拆成可在数分钟内完成和验证的步骤，并为每个步骤给出：

- 精确文件路径与预期符号。
- 先写的失败测试及预期失败原因。
- 最小实现范围。
- 目标测试命令和预期结果。
- 数据迁移、兼容路径和回滚检查。
- 建议的独立提交边界。

实施计划不得把“补测试”“处理异常”“优化动效”作为没有文件、断言和验证命令的笼统任务。

## 14. 设计确认点

书面确认本文后，实施计划将以以下决策为固定输入：

- 采用四项目顺序，不进行全量重写。
- 外部日历严格只读，本应用事件使用可重试清理。
- 笔记保存改为防抖 + 返回时 flush，销毁时不保存。
- 备份采用不可变代际 + 双清单发布，并记录有效空状态。
- 日期迁移为 LocalDate/epochDay，编辑器保持单日模型。
- 重复日历按 occurrence 建模。
- 业务提交与动画彻底解耦。
- 行为测试成为正确性的主要证据。
